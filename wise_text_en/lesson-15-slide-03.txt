Following One Sample

The sampled project is called Project Mariner. A consulting team prepared a draft market-entry memo for a technology client. In the project folder, Amira finds a draft paragraph that sounds different from the team's normal writing. The project manager explains that NexaOffice helped summarize several internal notes and client emails. The final memo was reviewed by a manager, but there is no record showing what was AI-assisted, what source material was used, or what review steps were performed.

This does not automatically create a nonconformity. It creates an evidence lead. Amira asks the consultant to describe the boundary for sensitive information. The consultant says customer names should not be entered. Then Amira asks whether project background, draft pricing assumptions, and non-public contract context may be entered if the customer name is removed. The consultant pauses. The training said do not input sensitive information, but it did not translate that rule into consulting scenarios.

The IT administrator then shows the enterprise console. Content logging is disabled for privacy reasons. That may be legitimate. But the organization still needs another way to monitor use risk. Amira asks whether metadata, sampling interviews, exception reports, prompt-category reports, or DLP alerts are reviewed. The administrator shows account-access logs, but no sampling review. The compliance manager shows training attendance, but no scenario-based test. The project manager shows review approval, but no AI-output review field.

Now the SoA gap becomes visible. The issue is not that the organization lacks every control. In fact, it has several useful pieces: a scoped tool, an approved platform, user rules, access control, training, and a supplier record. The gap is the connection among them. The SoA says use controls are implemented, but the sampled project cannot show how the use control operated when client information, AI drafting, management review, and customer delivery met in one workflow.

That distinction matters for judgement. A weak audit conclusion would say, the SoA is wrong. A more disciplined conclusion asks where the inconsistency sits. Is it an applicability problem, because the SoA selected the right theme but used too broad a rationale? Is it an implementation problem, because the rule was not translated into records? Is it an evidence problem, because the control may operate but cannot be demonstrated? Or is it a dynamic maintenance problem, because tool use expanded after the SoA was last updated?
