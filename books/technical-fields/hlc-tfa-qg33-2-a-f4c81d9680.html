  • 文件定位说明

本文件用于质量管理体系认证中 QG33-2 技术领域包的分组论证、审核员专业能力评价、授权控制、项目匹配、能力扩展和持续保持。本包为单小类独立技术领域包，重点说明计算机编程活动内部路线的共同质量形成基础、差异控制、抽样方法和能力授权边界。

本文件不把软件发行、计算机咨询、系统集成、设备管理、数据托管或门户网站纳入本包。相邻活动可作为背景经历，但不能替代代码实现、构建测试和交付转维的专业能力确认。

  • 技术领域包构成
小类编码小类名称纳入本包的活动范围主要内部路线特殊边界
33.02.01计算机编程活动需求分析、架构设计、程序编码、接口开发、数据库开发、脚本开发、测试、构建、部署准备、维护性开发和技术文档形成。客户定制开发、产品研发开发、前端、后端、移动端、接口和中间层、数据库和脚本、低代码/配置开发、维护性开发。本包以代码实现和可运行软件制品形成为核心；纯咨询、软件发行、系统集成实施和长期运维不属于本包主导活动。
  • 分组设立的基本逻辑

虽然本包只包含一个专业小类，但计算机编程活动内部路线跨度较大，需要形成独立技术领域包进行能力控制。QMS 关注的共同对象是软件开发交付物及其质量形成链：顾客需求或产品需求如何进入设计，设计如何进入代码，代码如何形成构建物，构建物如何通过测试、缺陷修复、配置管理和部署准备进入交付状态。

本包共同质量形成链为：需求输入 → 需求分析和设计 → 编码实现 → 代码评审 → 构建打包 → 测试验证 → 缺陷修复 → 版本冻结 → 部署资料和转维交接。无论前端、后端、移动端、接口、数据库、脚本、低代码还是维护性开发，均应围绕需求追溯、配置控制、构建可重复、测试充分、缺陷闭环和交付资料完整进行 QMS 判断。

内部差异主要表现为技术栈、交付对象、测试方法、部署环境和客户验收方式不同。这些差异不需要拆成多个领域包，但应通过内部路线标注、能力面谈、案例评审和项目匹配控制。

  • 专业小类关系类型与授权后果
关系类型含义授权后果典型控制方式
共同基础关系共享信息技术服务、需求识别、版本或配置控制、验证放行和反馈闭环等基础能力。可简化基础专业面谈，但仍应确认目标小类或目标路线的实际经历。资料评审、案例判断、专业面谈。
并列分支关系同属本技术领域包，但交付对象、过程重点或质量形成路径存在分支差异。应记录实际分支能力，不把同包经历理解为全分支能力。分支标注、限定使用、项目技术支持。
条件扩展关系已具备相邻分支能力，具备扩展基础，但目标路线仍有专门知识和证据要求。完成补充培训、案例评审、专业面谈或见证审核后方可扩展。培训考核、案例评审、见证审核。
专项确认关系涉及特殊平台、强内容属性、高可用服务、大规模数据或复杂集成边界。在项目使用前应进行专项确认，必要时配置技术专家支持。专项面谈、技术专家评审、项目前确认。
不可直接替代关系相关 IT 经历不足以证明目标小类的质量形成链能力。不得作为目标能力的单独授权依据。重新评价、补充经历或限定项目类型。
边界受控关系互联网服务、数据、内容、账号、版权、许可或客户行业要求改变使用边界。授权记录应写明边界，项目匹配时按实际服务内容确认。授权备注、合规类别清单、技术支持。
前端、后端、移动端、数据库等内部路线共享软件工程过程，但技术对象和验证方式不同。应记录实际开发路线，不把一种路线经历等同于全技术栈能力。路线标注、代码和测试案例面谈。
编程与软件发行编程形成代码和制品，发行控制发布渠道和许可。发行经历不能替代编程能力；编程经历扩展发行需另行确认发行链条。相邻包能力单独评价。
编程与系统集成二者都可能涉及部署和接口。集成实施经历不能替代源代码、构建和测试能力。以代码仓库、构建和缺陷案例确认。
  • 本体系共同能力基础
共同能力维度本包共同基础可共享的审核判断不能共享的边界
需求追溯各类编程活动均需把需求、用户故事、接口约束和验收准则转化为开发任务。能判断需求、设计、代码、测试和验收之间是否可追溯。具体业务领域知识、算法深度和嵌入式硬件约束不能默认共享。
设计和编码控制均需架构、模块、接口、数据和异常处理等设计和编码活动。能判断代码实现是否受控，代码评审和编码规范是否发挥作用。不同语言、框架、数据库、移动端和低代码平台能力需标注。
配置和构建均依赖代码仓库、分支、依赖、构建脚本和制品管理。能沿一个构建物追溯到源代码、依赖和构建记录。容器、移动应用、桌面软件和云原生构建方式不同。
测试验证均需单元、接口、集成、回归、性能或用户验收等验证活动。能判断测试是否覆盖关键功能、边界条件和变更影响。算法、实时、高并发、移动适配或数据脚本的测试方法差异需确认。
缺陷和交付闭环均需缺陷单、修复记录、回归结果、发布说明和转维资料。能沿缺陷追溯到代码修改、测试结果和交付状态。运维接手、客户现场部署和产品发行属于相邻包边界。
  • 本体系核心控制要求

本章所称关键质量特性，是指服务或软件交付结果中影响顾客可接受性的功能、性能、可用性、完整性、可追溯性、服务响应和交付一致性等特性。

QMS 审核应围绕软件开发质量形成链展开。应确认组织如何识别顾客要求、业务规则、接口约束、数据约束、性能约束和验收准则；如何把需求转化为架构、模块、数据库、接口和任务；如何控制代码仓库、分支、合并、依赖、构建脚本和配置；如何开展代码评审、静态检查、单元测试、接口测试、集成测试、性能测试和回归测试；如何处理缺陷、变更、技术债和版本冻结；如何形成部署说明、配置清单、用户文档、接口文档和转维交接资料。

对定制开发，应重点核对客户需求、变更控制和验收证据。对产品研发，应重点核对产品路线、版本分支、缺陷池和兼容性。对接口开发，应重点核对字段、协议、鉴权、错误码和日志。对低代码开发，应重点核对平台配置、扩展脚本和导出包。对维护性开发，应重点核对影响分析、回归和旧版本兼容。

  • 分小类或内部路线差异分析
小类/路线与本包共同基础主要差异差异对能力授权的影响控制方式
客户定制开发需求、设计、编码、测试和交付链条完整。需求变化、客户验收和现场环境约束突出。应确认合同需求和变更控制能力。客户项目案例、需求追溯和验收记录评审。
产品研发开发共享软件工程和配置管理基础。版本路线、兼容性、缺陷池和长期维护突出。应确认产品版本管理能力。产品版本、分支和缺陷闭环案例评审。
前端开发共享需求、代码、构建和测试基础。界面、交互、浏览器兼容和页面性能突出。仅有后端经历扩展前端时需确认前端技术栈。页面组件、兼容测试和用户体验问题案例。
后端开发共享编码、接口和测试基础。业务逻辑、数据库、并发、接口和日志突出。仅有前端经历扩展后端时需确认服务和数据能力。接口、数据库、性能和异常处理案例。
移动端开发共享代码、构建、测试和版本控制基础。终端适配、权限、离线、签名和应用包突出。应标注移动端经历。安装包、终端矩阵和权限案例评审。
接口和中间层开发共享设计、编码和测试基础。协议、字段、鉴权、错误码、幂等和日志突出。应确认系统间契约能力。接口文档、调用日志和联调缺陷案例。
数据库和脚本开发共享需求和测试基础。数据结构、脚本调度、数据一致性和回滚突出。应确认数据处理和数据库能力。脚本、数据校验和回滚记录评审。
低代码/配置开发共享需求转换和交付验证基础。平台配置、组件约束、扩展代码和导出包突出。应确认平台特性，不把低代码经历扩展为全代码开发。平台配置、权限和扩展脚本案例。
维护性开发共享缺陷修复和回归基础。既有代码理解、影响分析和兼容性突出。应确认旧系统分析和回归能力。缺陷单、影响分析和回归结果评审。
  • 分组合理性论证结论

QG33-2 作为单小类独立技术领域包是合理的。计算机编程活动内部虽然路线多样，但在 QMS 轴下均围绕需求到代码、代码到构建、构建到测试、测试到交付的质量形成链展开。共同能力足以支撑统一领域包使用。

本包使用时不得忽略内部路线差异。机构应采用“单小类领域包 + 内部路线能力标注 + 条件扩展 + 相邻包边界控制”的口径，确保审核员能力与项目实际开发对象相匹配。

  • 审核关键要点与抽样方法
抽样场景现场必看记录必查纵向追溯路径追问方向
一个新功能开发需求池、任务看板、代码仓库、测试环境。需求规格、设计、提交记录、测试用例、缺陷和验收记录。客户需求 → 设计任务 → 代码提交 → 构建 → 测试 → 验收 → 交付。需求变更如何控制；测试如何覆盖验收准则。
一次接口变更接口文档、联调环境、日志平台。字段变更、契约说明、测试记录、调用日志、缺陷单。接口需求 → 设计 → 代码 → 联调 → 日志 → 上下游确认。错误码和兼容如何处理；调用失败如何定位。
一个缺陷修复缺陷系统、代码差异、回归环境。缺陷单、根因分析、修复提交、回归结果、版本说明。用户问题 → 缺陷定位 → 代码修改 → 回归 → 发布说明。是否影响其他模块；重复问题如何预防。
一次构建发布准备流水线、制品库、配置库。构建日志、依赖清单、制品标识、配置说明、部署脚本。源代码 → 依赖 → 构建 → 制品 → 配置 → 部署准备。构建是否可重复；环境差异如何控制。
维护性开发项目旧代码库、影响分析、回归环境。变更申请、影响分析、修复方案、回归用例、交接资料。变更输入 → 影响分析 → 修改 → 回归 → 交接。旧系统知识如何保持；回归范围如何确定。
  • 能力扩展与条件授权
起点能力目标能力可扩展依据必须补充确认授权限制

  • 培训、考核与作业指导书需求

本包应建立软件工程 QMS 专业培训，内容包括需求工程、架构设计、代码和配置管理、构建和制品管理、代码评审、测试策略、缺陷闭环、版本冻结、部署资料和转维交接。内部路线培训应覆盖前端、后端、移动端、接口、数据库、低代码和维护性开发的差异。

考核应采用案例式题目，要求审核员沿一个需求、一个缺陷或一个构建物完成纵向追溯。作业指导书应提供需求追溯、代码仓库、构建流水线、接口变更、缺陷修复和维护性开发的抽样路径。

  • 常见合规义务类别与标准适用提示

本包可能涉及软件著作权、合同交付、开源组件许可、个人信息保护、数据安全、网络安全、电子签名、密码应用、特定行业信息系统接口、客户行业开发规范和软件工程标准类别。文件不列具体标准编号和年份；适用性应使用机构受控的现行有效清单、客户合同和项目资料确认。

这些类别用于识别外部要求如何转化为软件需求、设计约束、代码约束、测试要求和交付资料，不替代任何法定审批、行政监管或客户专门验收。

  • 分组使用限制和法定边界

本分组仅用于 QMS 认证中的技术领域包论证和审核员专业能力控制。管理体系审核不替代软件著作权登记、网络安全监管、个人信息和数据处理法定评估、密码应用合规判断、行政执法、客户行业准入评价或软件产品第三方测评。

当项目涉及高并发交易系统、个人信息密集处理、关键行业应用、密码功能、嵌入式实时控制、复杂算法、医疗金融政务等专门领域软件时，应追加专项确认或技术专家支持。

  • 分组结论与使用口径

QG33-2 可作为质量管理体系计算机编程活动独立技术领域包使用。授权时应记录审核员实际经历属于客户定制、产品研发、前端、后端、移动端、接口、数据库、低代码或维护性开发等路线。内部扩展应通过培训、案例评审、专业面谈、见证审核或技术支持控制。

文件维护触发条件包括：软件开发方法、云原生架构、低代码平台、AI 辅助开发、测试工具链、个人信息和数据处理边界、客户行业软件要求发生实质变化，或上层分组使用中出现能力匹配争议。
